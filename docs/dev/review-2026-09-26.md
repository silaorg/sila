# Code review, September 26

Heswe has a usable local app and a reasonable package split. Hosted execution still needs lifecycle work and a real Linux deployment test.

This pass follows both [review](../actions-for-agents/less-retarded.md) and [tidy](../actions-for-agents/tidy.md) guides. It covers the web API, workspace storage, agent workers, channel adapters, client refreshes, dependencies, and deployment docs.

Findings below come from source review unless a test result is stated. This is not a completed sandbox escape test.

## Keep the basic structure

The current responsibilities are easy to follow:

- `web` owns accounts, workspace ownership, HTTP, and live connections.
- `heswe` owns workspace files, thread history, channels, and the agent loop.
- `agents` runs that loop in a child process or a gVisor container.
- `client` owns the browser interface.
- AIWrapper and AIModels are pinned source dependencies.

Keep these boundaries. A new service layer around every class would add more work than clarity.

The shared thread queue and channel runtime already remove useful duplication. Keep Slack and Telegram transport details separate. Their input formats and file delivery differ.

## Fixed in this pass

### Worker shutdown could wait forever

`ProcessAgentRuntime.stop()` started its timeout after receiving the stop response. A worker ignoring that request never reached the timeout.

The deadline now covers the request and process exit. A regression test starts an unresponsive worker and verifies forced termination.

This stops the local child. Docker container cleanup remains separate work below.

### Failed launches left a broken worker cached

The runtime cleaned up on `exit`. Failed executable launches emit `error` and `close`, without `exit`.

Cleanup now waits for `close`. It also handles failed stdin writes. A regression test fails the first launch, then sends a message through a fresh worker.

Request serialization happens before registering pending work. Invalid input cannot leave a pending request behind.

### Progress callbacks could cause an unhandled rejection

The runtime queued callbacks but only handled their rejection after the final response. A slow response left a rejected promise unhandled.

Failures are now handled immediately and retained for the request result. The test delays the worker response after a failing callback.

### Initialization failures stayed cached

Auth cached a rejected initialization promise. SQLite published its connection before configuring it.

Auth now allows another initialization attempt. SQLite closes failed connections and caches only configured ones. Tests cover a failed database open and invalid database contents.

### Aborted event streams stayed open

Aborting a request removed the subscription and heartbeat but left the stream open.

Abort now closes the stream. Tests cover a pending read and independent subscribers.

### Thread details read history twice

Opening a thread read the log for its summary, then read it again for messages. A concurrent append could produce mismatched results.

Both now use one snapshot. A test verifies that the summary matches the returned history.

### Provider configuration used direct overwrites

Provider and default-agent JSON files bypassed the existing atomic writer.

They now use `writeJsonFile`. Readers see the previous or replacement file, rather than an incomplete overwrite. This does not make a settings update across multiple files transactional.

### Documentation overstated the API boundary

The hosted guide said thread responses contained no tool details or absolute paths. The UI receives tool names and argument previews. Those previews can contain paths.

The guide now describes what the code returns. Dependency instructions also flag the missing interim database migration.

## Next: workspace lifecycle

Priority: high before running a shared server.

[`AppWorkspaceService`](../../packages/heswe/src/app/app-workspace-service.js) drains a snapshot of its queues during reset and shutdown. It continues accepting new messages. A new thread can start on a runtime that settings changes are about to stop.

[`workspace-service.ts`](../../packages/web/src/lib/server/workspace-service.ts) keeps every service in a process-wide map. There is no eviction or application shutdown path for those services.

[`RunscAgentRuntime`](../../packages/agents/src/runsc-agent-runtime.js) delegates stop to the Docker client process. Killing that process does not explicitly stop or remove its named container. A surviving container can retain resources and block the next launch.

The worker also has no admission gate or drain of active requests during stop. Stdin closure can race with ongoing model work.

Use one owner for admission, reset, shutdown, and container cleanup. Start with a workspace admission barrier, then add deterministic container cleanup. Keep concurrent threads during normal operation.

See the [lifecycle proposal](proposals/workspace-runtime-lifecycle.md).

## Settings need one ordered update path

Priority: high before simultaneous settings edits.

[`updateWorkspaceModelSettings`](../../packages/heswe/src/providers.js) writes provider config, agent selection, and environment values separately. A failure midway leaves a partial update. Concurrent `.env` read-modify-write operations can overwrite each other's changes.

Atomic file replacement helps individual files. It does not order these operations or coordinate the runtime reset.

First serialize settings changes with the lifecycle owner. Validate all input before writes. Define when the new configuration becomes active and what a failed update leaves behind.

Avoid a general configuration framework. This needs one explicit update operation.

## Names and stored data

Priority: high when returning to a database from the interim Sila build.

The rename changed `sila_workspaces` and `sila_workspace_selections` to `heswe_` names. [`WorkspaceRegistry`](../../packages/web/src/lib/server/workspace-registry.js) creates the new tables but does not migrate the old ones.

Accounts can still exist while the workspace list appears empty. Files remain on disk. Changing the database environment variable alone does not fix ownership records.

Add a versioned migration with fixtures for old-only, new-only, and mixed databases. Preserve IDs and selections. Stop on conflicting records instead of silently choosing one table. Keep existing tables until the migration has been verified.

Stored identifiers should stay stable through future product renames. UI branding should not trigger another storage rename.

## Reconnects and refresh cost

Priority: medium for correctness and larger histories.

The server sends `connected` on every event-stream connection. [`api-client.ts`](../../packages/client/src/lib/api-client.ts) does not handle it. Changes missed during disconnection remain invisible until another invalidation or reload.

Each thread event also refreshes the full thread list. [`AppThreadRepository.list`](../../packages/heswe/src/app/app-thread-repository.js) reads every thread's history to build those summaries. A progress event can therefore cause work proportional to all stored messages.

First refresh the workspace, open threads, and files after reconnect. Coalesce overlapping invalidations. Then measure history reads before choosing a summary cache or index.

Do not replace this with token streaming just to avoid repeated reads. The current snapshot API can work well with narrower invalidations.

## Tool activity needs truthful states

Priority: medium.

[`projectToolActivities`](../../packages/heswe/src/app/app-workspace-service.js) marks every tool request as `complete`. It does not match requests with result records. An interrupted request can look finished, and a failure has no distinct state.

The runtime's progress helper also returns early when assistant text is empty. A tool-only model response can therefore miss its live activity indicator.

Define states from actual request and result events. Cover successful, failed, interrupted, and tool-only turns. Preserve useful assistant text alongside tool calls.

This changes the projection contract and UI expectations. Keep it as one focused follow-up.

## File operations are not a transaction

Priority: medium; high before claiming protection from hostile concurrent filesystem changes.

[`AppFileStore`](../../packages/heswe/src/app/app-file-store.js) checks paths and symlinks. Those checks are useful, and the existing tests cover static escapes.

Rename checks whether a destination exists, then calls `fs.rename`. Another writer can create that destination between the two operations. Batch moves attempt rollback, but rollback errors are discarded.

Path checks and later filesystem operations are also separate. An agent can modify workspace paths concurrently with the host API.

Define collision and partial-failure behavior first. Serialize API mutations where useful, but do not present that lock as protection against agent processes. Review descriptor-based access or moving file operations behind the workspace boundary before a hostile-workload deployment.

## History recovery needs a policy

Priority: medium before trusting long-running work to the server.

[`ThreadStore`](../../packages/heswe/src/thread-store.js) appends JSON lines and parses the full log strictly. An incomplete final write can make the whole thread unreadable.

Legacy `messages.json` support is a data migration path, not dead code. Keep it until an explicit migration removes the need.

Add fixtures for incomplete final records and corruption in the middle. Recover only where the policy is clear. Never silently discard valid earlier messages or rewrite damaged history without a backup.

## Production boundary remains incomplete

Priority: high before hosting other people's agents.

The launcher specifies gVisor, resource limits, a read-only root, and one workspace mount. Startup checks Docker, the image, and the network's existence.

It does not verify the network's firewall policy. Resource limits also do not bound JSON protocol lines, pending requests, or the API's event queues. A worker can flood the host-side reader.

Provider keys remain inside workspace `.env` files. Agents can read them. The proposed inference broker would change that model; it is not implemented.

Slack and Telegram still run their agents in their channel process. They do not yet share the hosted app's sandbox boundary.

Complete the existing [sandbox proposal](proposals/workspace-agent-sandboxing.md) in small steps. Start with Linux lifecycle tests, bounded protocol traffic, and verified network policy. A multi-server scheduler is not the first missing piece.

## Dependencies and delivery

Priority: high before sharing this branch for a fresh clone.

The submodule setup is sensible for this repository. The parent pins AIWrapper; AIWrapper pins AIModels. Keep builds on those recorded commits.

The selected AIWrapper commit `6c0b385` is still local. Publish it before publishing a parent commit that requires it. Otherwise another machine cannot fetch the selected dependency.

The `file:` dependency also makes the current Heswe package repository-dependent. Do not assume a standalone npm package will work. Decide its distribution format before publishing it.

This branch has no GitHub Actions workflows and no automated client interaction suite. Add CI for recursive checkout, installation, tests, checks, and build. Then cover workspace switching, reconnects, attachment retry, and tool activity in the browser.
